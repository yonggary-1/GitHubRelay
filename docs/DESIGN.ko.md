## 만든 목적

GitHub Relay는 채팅 세션에서 개발한 프로젝트를, 토큰을 세션에 넘기지 않고 안전하게 GitHub에 올리기 위해 만든다. 개발 중인 세션은 그대로 둔 채 결과물만 받아 릴리즈하는 것이 목표다.

해결하려는 문제는 두 가지다.

1. 접속 실패: 채팅 세션에 토큰을 주고 직접 업로드하게 했지만, 대부분의 세션이 GitHub에 도달하지 못했다.
2. 토큰 유출 위험: fine-grained 토큰을 채팅 세션에 넘기면 이후 그대로 탈취되어 repo가 해킹당할 위험이 남는다.

## 동작 개요

채팅 세션은 정해진 규격의 릴리즈 번들(zip)만 만들고, GitHub Relay가 로컬에서 검수한 뒤 GitHub에 커밋과 릴리즈를 올린다. 토큰은 사용자 PC 밖으로 나가지 않는다.

## 비공식 도구 표시

GitHub Relay는 GitHub, Inc.와 무관한 개인 제작 비공식 도구이며, 이 사실을 사용자가 놓칠 수 없는 위치에 영어와 한국어로 표시한다.

| 위치 | 표시 방법 |
| --- | --- |
| README 맨 위 | 언어 링크 바로 아래, 목적보다 먼저. 경고 상자(`> [!WARNING]`)로 강조 |
| 프로그램 창 하단 | 상태 표시줄에 "비공식 도구 · GitHub, Inc.와 무관" 상시 표시 |
| 프로그램 정보 창 | 버전, MIT 라이선스와 함께 같은 문구 |
| 릴리즈 노트 | 매 릴리즈 본문 끝에 한 줄 |

문구 (README 기준):

- 영어: "Unofficial tool. GitHub Relay is not made, endorsed, or supported by GitHub, Inc. "GitHub" is a trademark of GitHub, Inc."
- 한국어: "비공식 도구입니다. GitHub Relay는 GitHub, Inc.가 만들거나 보증·지원하는 프로그램이 아닙니다. "GitHub"은 GitHub, Inc.의 상표입니다."

핵심 원칙:

- 세션은 GitHub에 접근하지 않는다. 결과물만 만든다.
- 번들은 신뢰하지 않는 입력으로 다룬다. 업로드 전 반드시 검수한다.
- 사람이 변경 내용을 보고 승인해야만 업로드된다. 되돌릴 수 없는 작업(삭제 등)은 기본 버튼이 "아니요"다.
- 기록을 고쳐 쓰지 않는다. 강제 푸시를 하지 않고, 되돌리기도 새 커밋으로 한다.
- 실행 파일 하나와 데이터 파일 하나로 끝난다. 설치나 런타임이 필요 없다.

## 실행 환경과 파일 구성

Go로 빌드한 단일 exe이며, Windows 10/11 64비트(x64)에서 추가 설치 없이 실행된다. .NET, VC++ 재배포 패키지, WebView2, git 모두 필요 없다.

| 항목 | 결정 |
| --- | --- |
| 언어 | Go, GUI는 Win32 API 직접 호출 |
| 지원 OS | Windows 10 / 11, x64 |
| 미지원 | Windows 7 / 8 / 8.1 (Go 런타임이 Windows 10 이상 요구. 지원하려면 Go 1.20으로 별도 빌드) |
| ARM64 | 전용 빌드 없음. ARM용 Windows의 x64 에뮬레이션으로 실행될 가능성이 높으나 미확인 |
| 배포 형태 | 포터블. 설치 없음 |
| 파일 구성 | GithubRelay.exe + GithubRelay.dat (같은 폴더) |

데이터 파일 하나에 설정, 토큰, 업로드 기록을 모두 담는다. 데이터 파일이 없으면 첫 실행 때 새로 만든다.

쓰기 권한이 없는 폴더(예: Program Files)에 두면 데이터 파일을 저장할 수 없으므로, 개인 폴더에 두는 것을 전제로 하며 README에 명시한다.

## 화면 언어

모든 화면을 한국어와 영어로 제공하고, 창 상단의 라디오 버튼(한국어 / English)으로 즉시 전환한다. 선택한 언어는 데이터 파일에 저장되며, 첫 실행 때는 Windows 표시 언어를 따른다.

레이아웃 규칙:

- 버튼, 라벨, 표 머리글의 폭은 두 언어 중 긴 쪽을 기준으로 넉넉하게 잡는다.
- 언어를 바꿔도 글자가 겹치거나, 잘리거나, 다른 요소를 밀어내지 않아야 한다.
- 긴 안내 문구는 자동 줄바꿈되는 영역에 넣는다.
- 오류 메시지와 검수 결과도 선택한 언어로 표시한다.
- 릴리즈마다 두 언어로 모든 화면을 열어 확인하는 것을 테스트 항목에 넣는다.

## 화면 구성

자주 하는 일(릴리즈)이 첫 탭이자 시작 화면이고, 드물게 하는 리포지터리 관리는 마지막 탭이다.

| 순서 | 탭 | 하는 일 |
| --- | --- | --- |
| 1 | 새 버전 릴리즈 | 번들 검수와 업로드, 배치 릴리즈 (기능 2, 3) |
| 2 | 기록 | 업로드 기록, 동기화, 되돌리기·릴리즈 삭제 (기능 4) |
| 3 | 번들 규격 문서 | 채팅 세션에 줄 규격 문서 (기능 5) |
| 4 | 리포지터리 등록/관리 | 등록, 토큰 교체·검증, 주소 수정, 삭제 (기능 1) |

새 버전 릴리즈 탭 배치 (위에서 아래로):

1. 리포지터리 목록: 리포, 최신 버전, 토큰 상태. 여러 개면 스크롤. 마지막 선택을 기억하고, 다른 리포를 직접 고르면 검수 영역이 초기화됨
2. 요약 줄: 번들 파일 이름, 버전, 변경 수
3. 왼쪽: 처음에는 드롭 영역(안내 + 찾아보기). 번들을 넣으면 검수 목록, 여러 개면 배치 목록으로 바뀜. 아래에 **초기화**
4. 오른쪽: 변경 파일 목록. 아래에 **다시 검수**
5. 체크박스: 드래프트(배치에서는 비활성화), 워크플로 승인, 경고 확인
6. 상태 문구, 진행 막대, **릴리즈 페이지 열기**, **승인하고 업로드**(배치에서는 배치 시작/정지/이어서 진행)

창 아래는 모든 탭에 공통이다: 비공식 도구 문구, **업데이트 확인**, **정보**.

## 기능 1. 리포지터리 등록/관리

GitHub 리포지터리 주소와 그 리포 전용 토큰을 한 쌍으로 등록한다. 등록 순간 토큰을 실제로 검증하고, 통과해야 저장된다.

입력 항목: 리포지터리 주소(`소유자/이름`도 허용), fine-grained 토큰, 브랜치(비우면 기본 브랜치).

등록·검증 시 확인하는 것:

1. 리포가 있고 이 토큰으로 접근할 수 있는지
2. Contents 쓰기 권한이 있는지 (빈 리포는 첫 업로드 때 확인)
3. 토큰 만료일 (14일 전부터 목록에 경고, 시작할 때 알림)
4. GitHub의 고유 리포 ID (이름이 바뀌어도 같은 리포인지 판별하는 기준)

버튼:

- **등록 및 검증** / **토큰 교체** / **다시 검증**
- **주소 수정**: 리포 이름이나 소유자가 바뀐 뒤 새 주소로 옮김. 리포 ID가 같은 경우에만 허용하고, 토큰·기록은 그대로 이어짐
- **등록 삭제**: 토큰을 지우고, 기록을 함께 지울지 보관할지 물음 (보관한 기록은 다시 등록하면 돌아옴)
- **GitHub에서 열기** / **토큰 발급 페이지 열기**

이름 변경 자동 감지: 검수나 검증 중 GitHub이 다른 현재 이름을 알려주면, 등록 정보를 업데이트할지 묻는다. 이전 이름은 기억해서, 이전 이름이 적힌 번들은 경고와 함께 통과시킨다. 쓰기 요청은 GitHub 리디렉트에 기대지 않고 항상 현재 이름으로 보낸다.

토큰 발급 안내: 대상 리포 하나만 선택, 권한은 Contents: Read and write 하나, 만료일 설정. 릴리즈·태그 삭제와 되돌리기도 이 권한으로 동작한다.

## 기능 2. 새 버전 릴리즈

번들 zip 하나를 끌어다 놓거나 찾아보기로 고르면, 검수 → 변경 미리보기 → 승인 → 업로드 순서로 진행된다. 검수에서 하나라도 실패하면 업로드 버튼과 확인 체크박스가 모두 잠긴다.

진행 순서:

1. 번들 선택: `release.json`에 적힌 리포가 등록돼 있으면 목록에서 자동 선택
2. 검수: 로컬 검사 후 GitHub의 현재 상태와 비교
3. 변경 미리보기: 추가 / 수정 / 삭제 파일 목록
4. 승인: 드래프트 여부 선택(기본값: 바로 공개), 경고가 있으면 확인 체크, 확인 창
5. 업로드: 커밋 → 브랜치 갱신 → 릴리즈 → 첨부 파일, 단계별 진행 표시

검수 항목 (실패 = 업로드 불가):

- 필수 파일: `release.json`, `languages`의 모든 언어별 README와 릴리즈 노트, `src/`
- `release.json` 형식과 필수 필드, `spec_version`
- 대상 리포 일치 (이전 이름이면 경고만)
- 버전 규칙: 숫자 두 자리(0.1) 또는 세 자리(0.1.1). **GitHub에 실제로 있는 릴리즈 중 가장 높은 버전**보다 높아야 함. 이미 릴리즈된 버전은 메시지 하나로 안내
- zip 경로: `../`, 절대 경로, 드라이브 문자, 심볼릭 링크 차단
- 비밀 정보: GitHub 토큰, API 키, 개인키, `.env` 등. 바이너리 파일에서 우연히 걸린 경우는 경고
- 첨부 파일이 `dist/`에 실제로 있는지
- 다른 프로젝트 번들 차단: README·LICENSE 같은 공통 파일을 빼고 기존 파일과 20% 미만만 겹치면 실패 (빈 리포와 파일 5개 미만은 제외)

경고 항목 (확인 후 진행):

- `.github/workflows/` 추가·변경 (별도 체크 필요)
- 기존 파일의 30% 초과 삭제, 50MB 초과 파일
- 규격에 없는 파일(무시됨), 바뀐 파일 없음

번들은 리포 전체 스냅샷으로 취급한다. 번들의 `src/`에 없는 파일은 리포에서 삭제된다.

## 기능 3. 배치 릴리즈

번들 zip을 여러 개 한꺼번에 놓거나 찾아보기에서 여러 개를 고르면 배치가 된다. 모두 같은 리포용 번들이라고 가정하고, 버전 순서대로 차례로 릴리즈한다.

1. 사전 점검: 모든 번들을 로컬에서 먼저 검사(형식, 비밀 정보, 같은 리포인지, 중복 버전·태그). 하나라도 실패하면 시작 불가
2. 정렬: `release.json`의 버전 순서(0.9 다음 0.10). 파일 이름 순서와 다르면 안내
3. **배치 시작** 한 번으로 확인. 각 번들은 올리기 직전에 GitHub과 비교해 다시 검수
4. 실패하면 그 번들에서 정지. GitHub 비교에서 경고가 나오면 올리기 전에 물음(거절 시 일시 정지)
5. **정지** / **이어서 진행**. 이미 릴리즈된 버전은 건너뛰므로 멈춘 배치는 같은 번들을 다시 놓아 이어갈 수 있음

배치는 항상 바로 공개한다. 드래프트로 여러 개를 올리면 웹에서 하나씩 공개해야 하고 "Latest" 표시가 엉킬 수 있기 때문이다. 목록에서 번들을 더블클릭하면 전체 검수 결과를 보여준다.

## 기능 4. 기록과 릴리즈 바로잡기

리포별로 언제 어떤 버전이 올라갔는지 보여주고, 잘못 올린 릴리즈를 바로잡는다.

기록 목록 (최신순): 일시, 버전, 상태, 변경(추가/수정/삭제), 브랜치, 비고.

| 상태 | 뜻 |
| --- | --- |
| 공개됨 / 드래프트 | 이 프로그램으로 올린 릴리즈 |
| 커밋됨, 릴리즈 미완료 | 커밋은 올라갔지만 릴리즈 생성에 실패 |
| 실패 | GitHub에 아무것도 바뀌지 않음 |
| GitHub에서 가져옴 / 삭제됨 | 동기화로 찾거나 웹에서 지워진 것을 확인한 릴리즈 |
| 릴리즈 삭제함 (커밋 유지) | 이 프로그램으로 삭제한 릴리즈 |
| 이 버전 파일로 되돌림 | 그 버전으로 되돌린 커밋 |

버튼: **GitHub와 동기화**, **릴리즈 페이지 열기**, **커밋 보기**, **릴리즈만 다시 시도**, **이 버전으로 되돌리기**, **릴리즈 삭제**.

리포에는 따로 움직이는 두 얼굴이 있다. 코드(Code 탭)와 릴리즈(다운로드, "Latest" 표시)다.

| 작업 | 코드 | 릴리즈 | 함께 물어보는 것 |
| --- | --- | --- | --- |
| 이 버전으로 되돌리기 | 그 버전 파일로 (새 커밋) | 그대로 | 이후 릴리즈도 삭제할지 |
| 릴리즈 삭제 (최신) | 그대로 | 릴리즈·첨부 파일·태그 삭제, Latest는 직전으로 | 코드도 직전 버전으로 되돌릴지 |
| 릴리즈 삭제 (중간) | 그대로 | 그 릴리즈만 삭제 | 없음 |

- 두 작업은 독립적이라 순서는 상관없다. 둘 다 하면 잘못 올린 릴리즈가 완전히 취소된다.
- 코드 되돌리기가 실패하면 함께 하려던 릴리즈 삭제도 하지 않는다.
- 삭제한 버전으로는 되돌릴 수 없다. 삭제한 최신 버전은 다시 올릴 수 있지만, 중간 버전은 더 높은 릴리즈가 남아 있어 다시 올릴 수 없다.
- 확인 창의 기본 버튼은 "아니요" 또는 "취소"다.

## 기능 5. 번들 규격 문서 출력

채팅 세션에 그대로 붙여넣을 규격 문서를 현재 화면 언어(한국어/영어)로 만든다. **클립보드로 복사**와 **.md 파일로 저장**을 제공한다.

- 대상 리포지터리는 항상 "(지정 안 함)"으로 시작한다. 자동으로 고르면 엉뚱한 리포용 문서가 나가는 사고가 있었기 때문이다.
- 리포를 고르면 문서 맨 위에 "이 리포 전용"이라고 표시하고, 주소와 직전 버전, 권장 다음 버전을 채운다.
- 고르지 않으면 `OWNER/REPO`, 버전, 파일 이름이 모두 **예시**라고 표시하고, 실제 값은 추측하지 말고 사용자에게 물어보라고 안내한다. 이 상태로 복사·저장하면 확인 창을 띄운다.

번들 구조 (규격 v1):

```
<리포>-v<버전>-bundle.zip
├─ release.json             필수. 릴리즈 정보
├─ README.md                필수. languages 첫 번째 언어
├─ README.<코드>.md          나머지 언어마다 필수
├─ RELEASE_NOTES.md         필수. languages 첫 번째 언어
├─ RELEASE_NOTES.<코드>.md   나머지 언어마다 필수
├─ src/                     필수. 리포에 커밋될 전체 소스 (스냅샷)
└─ dist/                    선택. 릴리즈에 첨부할 빌드 결과물
```

`release.json` 예시:

```json
{
  "spec_version": 1,
  "repo": "yonggary-1/GitHubRelay",
  "version": "1.0",
  "tag": "v1.0",
  "title": "GitHub Relay v1.0",
  "commit_message": "Release v1.0",
  "languages": ["en", "ko"],
  "assets": ["dist/GithubRelay.exe"]
}
```

- 각 README 맨 위에 다른 언어 링크, 첫 단락에 만든 목적을 적는다.
- 릴리즈 노트는 언어별 파일을 합쳐 릴리즈 본문 하나로 올린다.
- 금지 사항: 토큰·키 등 비밀 정보, `.env` 같은 비밀 파일, 위험한 zip 경로, 요청하지 않은 워크플로 추가.

## 기능 6. 자동 업데이트

이 프로그램 자신의 리포(`yonggary-1/GitHubRelay`, 코드에 고정)에서 새 버전을 확인하고 설치한다. 토큰은 필요 없다.

1. 시작할 때(또는 **업데이트 확인** 버튼) 최신 공개 릴리즈를 확인
2. 새 버전이 있으면 안내: [예] 지금 업데이트(자동 재시작), [아니요] 다음에 알림, [취소] 이 버전 건너뛰기
3. 새 `GithubRelay.exe`를 받아 크기, GitHub이 공개한 SHA-256, Windows 실행 파일 여부를 검증
4. 현재 exe를 `.old`로 바꾸고 새 파일로 교체, 새 버전 실행 후 현재 창 종료
5. 새 버전이 시작하면 `.old` 삭제

- 데이터 파일은 건드리지 않는다. 검증이나 교체가 실패하면 현재 버전이 그대로 남는다.
- 업로드나 배치 작업 중에는 업데이트를 막는다.
- 릴리즈에 실행 파일이 없으면 릴리즈 페이지를 여는 안내로 대신한다.

## GitHub 작업 방식

git 프로그램 없이 GitHub REST API만으로 커밋과 릴리즈를 만든다. 결과는 일반 git push와 같은 정상 커밋 히스토리로 남는다.

업로드:

1. 브랜치의 현재 커밋과 파일 목록 조회
2. 바뀐 파일만 blob으로 업로드 (git 해시로 비교)
3. 번들 내용만으로 새 tree 생성 (번들에 없는 파일은 삭제됨)
4. 현재 커밋을 부모로 새 커밋 생성
5. 브랜치 갱신 (강제 없음. 검수 이후 브랜치가 바뀌었으면 아무것도 바꾸지 않고 중단)
6. 그 커밋에 태그를 붙여 릴리즈 생성, `dist/` 첨부 파일 업로드

- 빈 리포: `README.md` 하나로 첫 커밋을 만든 뒤 일반 순서로 진행
- 5단계 이후 실패: "커밋됨, 릴리즈 미완료"로 기록하고 **릴리즈만 다시 시도** 제공

되돌리기: 대상 버전 커밋의 tree를 그대로 사용해, 현재 커밋을 부모로 하는 새 커밋을 만든다. 파일을 다시 올리지 않으며, 커밋을 모르는 외부 릴리즈는 태그에서 커밋을 찾는다.

릴리즈 삭제: 릴리즈(첨부 파일 포함)를 지우고 태그 ref를 지운다. 커밋은 남는다.

## 보안 설계

토큰은 Windows 계정 기반 암호화(DPAPI)로 데이터 파일 안에 저장한다. 다른 PC나 다른 Windows 계정에서는 토큰을 풀 수 없다.

- 다른 PC로 옮기면 설정과 기록은 그대로, 토큰만 "재입력 필요"가 된다.
- 토큰은 화면, 로그, 오류 메시지 어디에도 평문으로 남기지 않는다.
- 토큰을 쓰는 통신은 `api.github.com`과 `uploads.github.com`뿐이다. 업데이트 확인과 다운로드는 토큰 없이 GitHub 공개 주소만 쓴다. 모두 HTTPS.
- 번들 zip은 디스크에 풀지 않고 메모리에서 읽는다.
- 리포당 토큰 하나, 권한은 Contents 쓰기 하나로 피해 범위를 그 리포로 한정한다.
- 한계: 같은 Windows 계정에서 실행되는 다른 프로그램은 DPAPI로 토큰을 풀 수 있다. 그래서 토큰 권한과 만료일을 최소로 둔다.
- 하나의 데이터 파일에는 한 번에 하나의 창만 열린다 (서로 덮어쓰기 방지).
